# Generation Provider Configuration — Design

## Boundary and data flow

The current uncommitted implementation has one OpenAI-compatible transport in `src/providers/generation.ts`. Preserve its extraction/mental prompts, local contract validation, one bounded repair, usage recording and evidence gates. Add a native Ollama transport behind the same generation client contract; `Worker` never branches on provider when it processes candidates, Jev or publications.

`panel draft → validated non-secret profile → separate durable staged revision → service restart → immutable active profile + server credential → transport → candidate/mental provenance`.

The profile is `{ protocol: "openai-compatible" | "ollama", baseUrl, model, authMode: "bearer" | "none" }`. OpenAI-compatible requests use `/chat/completions`; native Ollama uses `/api/chat`, `stream:false`, final `done:true`/`done_reason:"stop"` assistant text and native token counters. For either adapter, the reported model must match the configured model according to that adapter's documented identity rules. Unknown protocols, incomplete output and model substitution stop without a second provider request. Initial profile remains Antigravity with the verified `gemini-3.7-flash-medium` ID. Native Anthropic/Gemini are not supported in this batch.

## Configuration and activation

Use a separate revisioned generation-profile record, not `Settings.policy` or its revision: a provider edit must not invalidate Jev policy or overwrite ordinary settings. `src/contracts/index.ts` owns the public profile/status schemas. `Store` persists only the non-secret staged profile and a non-secret active fingerprint with revision/CAS; no credentials, raw response bodies or model output enter that profile record. On startup, resolve the staged profile if present, otherwise the server environment/defaults; validate it, resolve server-only credentials and freeze the active profile before starting the worker or accepting jobs. A save changes only the staged revision. The running worker and newly created jobs continue to use the startup profile until restart. `GET /api/overview` (or a dedicated same-origin profile endpoint) exposes active and staged non-secret values, configured-presence booleans and `restartRequired`; a dedicated CAS write does not use the existing `PUT /api/settings` policy revision. The settings panel reuses its dirty-draft, stale-revision and mutation conventions, shows the restart requirement and never renders a key input or value. Malformed persisted selections fail startup visibly; there is no fallback to the prior provider.

`authMode:"bearer"` uses `GENERATION_API_KEY`/`GENERATION_API_KEY_FILE` on the server and requires an explicit credential-origin match; the existing default/environment base URL pins the key's origin for backward compatibility, while switching origins requires an explicit `GENERATION_API_KEY_ORIGIN` plus a matching server-side key. Remote authenticated endpoints use HTTPS; the currently selected HTTP Antigravity endpoint is loopback. `authMode:"none"` is allowed only for a loopback literal endpoint and sends no Authorization header even if an unrelated key is present. URL parsing rejects userinfo, query, fragment and unsupported schemes; requests disable redirects and do not accept a destination from conversation/model output. Missing required credentials prevent generation, never trigger another adapter. Existing Ollama installations explicitly select native Ollama and migrate their credential to the server generation key source; there is no covert alias or automatic provider fallback.

## Durable work and migration

Record the active non-secret profile fingerprint on every job at creation, including never-started jobs. `Store.createJobInTx` reads the boot-activated fingerprint from its own configuration state, so manual import, background capture and reprocess use one authority. Add a nullable job column in a forward-only SQLite migration; existing rows with unknown fingerprints fail closed when unfinished rather than guessing which provider created them. On startup with a changed active fingerprint, a queued/retryable old job is marked failed with a visible configuration-change code before any provider/Jev/SiYuan call. An ordinary retry refuses a mismatched fingerprint; explicit reprocess creates a new run under the active fingerprint. The existing segment extraction plan still includes redacted input, prompt revision, protocol, endpoint and model; a partial extraction never resumes with a different plan. Candidates, mental cards, existing verified operations and immutable receipts are not rewritten. A credential rotation for the same approved origin/profile does not invent a new generator identity; changing protocol/endpoint/model/auth mode does.

## Risks and verification

- Profile-save/restart races: `Worker` uses an immutable startup snapshot; the separate CAS revision prevents a second tab from overwriting a newer staged profile.
- Secret leakage: verify `/api/overview`, profile read/write responses, audit/errors and DOM contain only presence; negative redirect and mismatched-origin cases send no credential.
- Local no-auth: a synthetic local endpoint must observe no Authorization header; Jev's retention gate remains mandatory.
- Legacy/restart: migrate a copy of an old SQLite fixture and verify both partially extracted and never-started jobs stop until explicit reprocess. Do not touch the production volume or formal deployment.
- Smoke both actual protocol entry points against isolated synthetic local servers; provider mocks alone are insufficient for the wire contract. Use a temporary data directory and no production SiYuan destination. Browser-check saved/pending/active status and conflict preservation on the actual local panel.

Rollback of code should not roll back the migrated database file. Use an isolated backup before any future production rollout; this task does not authorize that rollout, real provider calls or reprocessing.
